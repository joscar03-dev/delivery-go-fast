Sección 1: Análisis de Diagnóstico: Por Qué Fallan los Números Reales (El Mito del Plan Blaze)

1.1. El Verdadero Problema: Verificación de Aplicación vs. FacturaciónEl problema central encontrado —la autenticación telefónica de Firebase funciona con números de prueba pero falla con números reales— es un escenario común y un punto crítico de confusión para los desarrolladores. La acción de actualizar el proyecto de Firebase del plan Spark al plan Blaze es un prerrequisito de facturación.1 Firebase Phone Auth, clasificado como un producto de pago, requiere un plan de pago por uso (Blaze) para operar más allá del nivel gratuito, que es esencialmente inexistente para el envío de SMS a números reales.3Sin embargo, completar esta migración de facturación solo satisface los requisitos comerciales de Google; no aborda el requisito técnico de seguridad.El verdadero problema es un fallo en la "Verificación de Aplicación" (App Verification). Los números de teléfono de prueba (ej. +1 650-555-3434 con el código 123456) están explícitamente diseñados para omitir (bypass) todos los mecanismos de seguridad de Firebase.4 Esto permite a los desarrolladores probar la lógica de su aplicación sin configurar el complejo entramado de confianza de la plataforma.Cuando se utiliza un número de teléfono real, Firebase activa inmediatamente sus protocolos de seguridad para prevenir abusos, como el "SMS pumping".7 Firebase debe verificar que la solicitud de inicio de sesión proviene de una instancia legítima y autorizada de su aplicación. Si esta verificación falla, Firebase bloquea silenciosamente la solicitud de envío de SMS, resultando en el fallo que se está experimentando.8 El problema no es que el plan Blaze no esté funcionando; es que la aplicación no ha sido configurada para demostrar su identidad a Firebase.1.2. La Fragmentación de la Verificación por PlataformaEl desafío se intensifica por el hecho de que "App Verification" no es un único ajuste. Es un concepto que se implementa de manera drásticamente diferente en cada plataforma. Una aplicación híbrida, como una construida con Ionic y Angular (presumiblemente usando Capacitor), debe ser considerada como tres aplicaciones distintas a los ojos de Firebase: una aplicación de Android, una aplicación de iOS y una Aplicación Web Progresiva (PWA).Cada plataforma tiene su propio mecanismo de confianza principal:Android: Requiere la verificación de la integridad del dispositivo a través de la API Play Integrity (la sucesora de SafetyNet) 10 y la validación de la firma de la aplicación mediante huellas digitales SHA-1 y SHA-256.6iOS: Utiliza Notificaciones Push Silenciosas a través del Servicio de Notificación Push de Apple (APNs) como método principal de verificación.13Web / PWA: Depende de la verificación reCAPTCHA para demostrar que la solicitud es iniciada por un humano y desde un dominio autorizado.4El fallo del desarrollador se debe a que, al usar solo números de prueba, nunca fue necesario configurar ninguno de estos tres mecanismos de verificación. Para que los números reales funcionen, los tres deben estar correctamente configurados.1.3. Sección 2: El Desafío Central de Ionic: El Puente de Autenticación Híbrida

2.1. El Problema: El SDK Web (@angular/fire) en una WebView Nativa
La mayoría de los desarrolladores que comienzan con Ionic y Angular integran Firebase usando el paquete @angular/fire. Es fundamental entender que @angular/fire es principalmente un contenedor conveniente alrededor del SDK de Firebase JS (Web).

Este SDK web está diseñado para ejecutarse en un navegador. Como tal, cuando se le pide que verifique una aplicación para la autenticación telefónica, su único mecanismo disponible es el RecaptchaVerifier. Esto funciona perfectamente cuando la aplicación se ejecuta en un navegador web (por ejemplo, con ionic serve o desplegada como una PWA en Firebase Hosting).

2.2. El Fallo Crítico: reCAPTCHA en capacitor://
Aquí radica el núcleo del problema híbrido. Cuando la aplicación Ionic se compila nativamente usando Capacitor para la plataforma iOS, ya no se ejecuta desde un dominio https://. En su lugar, se sirve localmente desde el dispositivo usando el protocolo nativo capacitor://localhost.

El servicio reCAPTCHA de Google, por razones de seguridad, está diseñado para funcionar solo en orígenes http:// o https:// válidos. Cuando el SDK web de Firebase intenta instanciar un RecaptchaVerifier desde un origen capacitor://, el servicio de reCAPTCHA falla.

Esto crea un punto muerto: la autenticación telefónica en un dispositivo iOS nativo, cuando se usa el SDK web (@angular/fire), está destinada a fallar. La aplicación intentará recurrir a reCAPTCHA (ya sea porque APNs no está configurado o como respaldo) y fallará con un error interno, una pantalla en blanco o simplemente no haciendo nada.

2.3. La Solución Arquitectónica: El Plugin Nativo de Capacitor
La única solución arquitectónicamente sólida es no utilizar el SDK web de Firebase para la autenticación en compilaciones nativas. En su lugar, se debe emplear un plugin de Capacitor que actúe como un puente hacia los SDK nativos de Firebase (el Firebase iOS SDK y el Firebase Android SDK).

El plugin recomendado y mantenido activamente para esta tarea es @capacitor-firebase/authentication.

Este plugin, cuando se llama desde el código de Angular, no ejecutará el SDK de JS. En su lugar, invocará directamente el método nativo de iOS (que utiliza APNs) o el método nativo de Android (que utiliza Play Integrity). Esto omite por completo el problemático RecaptchaVerifier dentro del entorno de la WebView nativa.

2.4. El Plan de Implementación: El Servicio Híbrido
Este informe no sugiere reemplazar @angular/fire por completo, ya que sigue siendo necesario para la versión PWA/web de la aplicación. La solución correcta es una implementación híbrida.

Se debe crear un servicio de Angular (por ejemplo, PhoneAuthService.ts) que inyecte el servicio Platform de Ionic. Este servicio utilizará una lógica condicional simple:

Si platform.is('capacitor') es verdadero (es decir, la aplicación se está ejecutando como una aplicación nativa de iOS o Android), el servicio llamará a los métodos del plugin @capacitor-firebase/authentication.

Si platform.is('capacitor') es falso (es decir, la aplicación se está ejecutando en un navegador web), el servicio llamará a los métodos del SDK web (firebase/auth o @angular/fire) e inicializará el RecaptchaVerifier.

Este enfoque de "puente híbrido" proporciona una única API de autenticación para la aplicación Angular mientras se maneja la lógica de verificación de plataforma drásticamente diferente bajo el capó.
