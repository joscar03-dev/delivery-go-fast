Informe de Arquitectura e Implementación: Notificaciones Push en Tiempo Real para Aplicaciones de Delivery con Ionic, Angular y Firebase (2025)

Sección I: Arquitectura de Notificaciones en Tiempo Real para una Aplicación de Delivery

La implementación de un sistema de notificaciones push fiable es un componente de misión crítica para una aplicación de delivery. El valor de la plataforma depende de su capacidad para comunicar eventos de estado en tiempo real (p. ej., "Nuevo Pedido", "Pedido en Camino", "Pedido Entregado") a las partes correctas (restaurante y cliente), independientemente de si la aplicación está en primer plano, en segundo plano o completamente cerrada.

Este informe detalla la arquitectura y el plan de implementación de nivel de producción para lograr este sistema utilizando Ionic 6/7 (con Angular), Capacitor 5/6 y Firebase, centrándose en las mejores prácticas actuales (2024/2025) para garantizar la máxima fiabilidad.

Flujo de Datos de Extremo a Extremo

El sistema propuesto no consiste simplemente en "enviar notificaciones". Es una arquitectura reactiva, impulsada por eventos, que utiliza Firebase como un backend centralizado. El flujo de datos opera de la siguiente manera:

  1. Registro del Dispositivo (Cliente/Restaurante): La aplicación Ionic/Angular se inicializa, solicita permisos de notificación y se registra en Firebase Cloud Messaging (FCM). FCM devuelve un Token de Registro de Dispositivo (Token FCM) único.
  2. Almacenamiento del Token (Backend): La aplicación cliente envía este Token FCM a la base de datos (Cloud Firestore), donde se almacena y se asocia con el usuario o restaurante específico.
  3. Inicio del Evento (Fuente de Verdad): La lógica de negocio (p. ej., un cliente que realiza un pedido, un repartidor que actualiza el estado) modifica un documento en Cloud Firestore. Por ejemplo, el documento pedidos/12345 cambia su campo status de 'pendiente' a 'en_camino'.
  4. Detección del Evento (Backend): Una Cloud Function de Firebase, que actúa como un listener del backend, detecta este cambio en la base de datos (p. ej., un trigger onUpdate en la colección pedidos).1
  5. Lógica de Negocio y Enrutamiento (Backend): La Cloud Function identifica a quién se debe notificar (p. ej., el userId asociado con el pedido). Busca el o los Tokens FCM para ese userId en Firestore.3
  6. Construcción y Envío del Mensaje (Backend): La función construye un payload de mensaje específico (ver Sección VII) y utiliza el Firebase Admin SDK para enviar este mensaje a los servidores de FCM.4
  7. Entrega (Plataforma Nativa): Los servidores de FCM enrutan el mensaje al servicio de plataforma apropiado: el Apple Push Notification service (APNs) para iOS o el transporte de FCM para Android.6
  8. Recepción (Dispositivo): El sistema operativo del dispositivo recibe la notificación y la muestra al usuario, incluso si la aplicación está cerrada.

Requisito No Negociable: Diseño Impulsado por Eventos

La solicitud del usuario de notificar sobre "cambios de estado" dicta la arquitectura [Consulta del Usuario]. Intentar gestionar esta lógica desde el lado del cliente (p. ej., hacer que la aplicación del cliente envíe una notificación directamente a la aplicación del restaurante) es inseguro, poco fiable y propenso a fallos.

El estado de la aplicación (el estado del pedido) reside en Cloud Firestore. Por lo tanto, la "fuente de verdad" para cualquier notificación debe ser un cambio en un documento de Firestore. Las Cloud Functions son la herramienta nativa de Firebase diseñada explícitamente para "escuchar" estos cambios de base de datos (onCreate, onUpdate, onDelete) y ejecutar lógica de backend segura y fiable en respuesta.1 La implementación de triggers de Firestore no es opcional; es el pilar de un sistema de notificaciones robusto.

Decisión de Arquitectura Crítica: El Modelo de Datos del Token (Uno-a-Muchos)

Un error común en las implementaciones simples es almacenar un Token FCM en el documento users/{userId}. Esta arquitectura fallará en el caso de uso del delivery:

  • Fallo del Cliente: Si un cliente inicia sesión en su teléfono y luego en su tablet, el nuevo token de la tablet sobrescribirá al del teléfono. El teléfono dejará de recibir notificaciones.
  • Fallo del Restaurante: Un restaurante tendrá múltiples dispositivos (tablets en la cocina, teléfono del gerente). Si solo se almacena un token, solo el último dispositivo que inició sesión recibirá el "Nuevo Pedido", lo que es catastrófico.

La arquitectura de datos correcta debe soportar una relación de uno-a-muchos para los tokens. La solución es almacenar los tokens en una subcolección dedicada dentro del documento del usuario o restaurante.8

Modelo de Datos de Firestore Recomendado:

  • users/{userId}/fcmTokens/{tokenId}
  • restaurants/{restaurantId}/fcmTokens/{tokenId}

Cada documento dentro de esta subcolección contendrá, como mínimo:

  • token: El Token FCM real.
  • platform: 'ios' o 'android'.
  • createdAt: Un timestamp de cuándo se agregó el token.

Esta estructura 8 permite que un solo usuario o restaurante tenga múltiples dispositivos activos. Cuando la Cloud Function (Sección VI) se dispara, no buscará un token, sino que consultará esta subcolección y enviará el mensaje a todos los tokens activos, asegurando que todos los dispositivos relevantes sean notificados simultáneamente.4

Sección II: Configuración Fundacional del Proyecto (Capacitor y Firebase)

Antes de configurar las plataformas nativas, la base del proyecto Ionic y Firebase debe estar correctamente establecida.

Instalación del Plugin de Capacitor

El ecosistema de Capacitor proporciona un único plugin oficial que gestiona las SDK nativas de FCM (Android) y APNs (iOS).11 No se requieren otros plugins de push o FCM de Cordova o Capacitor.

Desde la raíz de su proyecto Ionic, ejecute:

Bash

npm install @capacitor/push-notifications

Este comando instala el plugin de Capacitor que proporciona la API de TypeScript para interactuar con los servicios de notificación nativos.12

Sincronización del Proyecto Nativo

Después de instalar cualquier plugin de Capacitor, se debe sincronizar el proyecto. Este paso crucial inyecta el código nativo del plugin en las carpetas de la plataforma android e ios.

Bash

npx cap sync

Este comando leerá el capacitor.config.ts, detectará el nuevo plugin de push-notifications y modificará los archivos de compilación nativos (como build.gradle y Podfile) para incluir las dependencias nativas requeridas, como la SDK de Firebase Messaging.12

Creación del Proyecto Firebase

Diríjase a la Consola de Firebase y cree un nuevo proyecto (o utilice uno existente).12 Este proyecto albergará los servicios de Cloud Messaging (FCM), Cloud Firestore y Cloud Functions.

El appId: El Identificador Unificado Crítico

El punto de fallo más común y difícil de depurar es un desajuste del identificador de la aplicación. Un solo valor, el appId en su archivo capacitor.config.ts, actúa como la "llave maestra" que conecta cuatro sistemas distintos:

  1. Su proyecto Ionic/Capacitor.
  2. Su proyecto nativo de Android.
  3. Su proyecto nativo de iOS.
  4. Su proyecto de Firebase.

Este valor (p. ej., com.midelivery.app) debe definirse primero en capacitor.config.ts 14 y luego copiarse textualmente en todas las demás configuraciones:

  • Firebase (Android): Usado como el "Nombre del paquete de Android".12
  • Firebase (iOS): Usado como el "ID de paquete de iOS".15
  • Apple Developer Portal: Usado como el "Bundle ID".16

Si hay un desajuste, el sistema fallará silenciosamente. La Consola de Firebase informará que el mensaje fue "enviado", pero el sistema operativo del dispositivo nunca lo entregará a su aplicación porque el appId del payload de la notificación no coincide con el appId de la aplicación instalada.

Sección III: Configuración Completa de la Plataforma Android

La configuración de Android requiere vincular el proyecto de Firebase con el código nativo de Android y, fundamentalmente, configurar Canales de Notificación para alertas de alta prioridad.

Registro de la App Android en Firebase

  1. En el dashboard de su proyecto de Firebase, haga clic en el icono de Android para "Agregar aplicación".12
  2. Nombre del paquete de Android: Ingrese exactamente el appId de su archivo capacitor.config.ts.12
  3. Apodo de la app: (Opcional, p. ej., "Delivery App Android").
  4. Certificado de firma de depuración SHA-1: (Opcional por ahora, pero recomendado para producción).
  5. Haga clic en "Registrar app".

Colocación del Archivo google-services.json

Firebase proporcionará un archivo google-services.json para descargar.12 Este archivo contiene las claves de la API que la SDK de Android necesita para conectarse de forma segura a su proyecto de Firebase.

  1. Descargue el archivo google-services.json.
  2. Coloque este archivo en el directorio a nivel de módulo de su proyecto Android. En una estructura de Capacitor estándar, esta ubicación es: android/app/.11
  3. Después de colocar el archivo, ejecute npx cap sync 12 nuevamente para asegurarse de que el sistema de compilación de Android lo reconozca.

En raras ocasiones, debido a conflictos de plugins, el sistema de compilación de Android puede buscar este archivo en una ubicación incorrecta.18 Si la compilación falla con un error de "archivo google-services.json no encontrado", abra el proyecto android en Android Studio y verifique manualmente la ubicación y la configuración en el archivo build.gradle a nivel de app.

Requisito Crítico (2025): Implementación de Canales de Notificación

Para cualquier aplicación dirigida a Android 8.0 (API 26) o superior, las notificaciones deben ser asignadas a un "Canal de Notificación".19 Este es un requisito del sistema operativo "ACTUAL" y es fundamental para su caso de uso.

Si no se especifica un canal, Android utilizará un canal predeterminado de baja prioridad. Esto significa que las notificaciones críticas de "Nuevo Pedido" pueden no emitir sonido, no vibrar y no aparecer en la pantalla de bloqueo. Para que la notificación "tenga que salir" [Consulta del Usuario], debe crear un canal de alta prioridad.

El plugin de Capacitor permite crear canales mediante programación desde su código Ionic/Angular.20 Esta llamada debe realizarse en la inicialización de la aplicación (ver Sección V).

Ejemplo de Creación de Canal (TypeScript):

TypeScript

import { PushNotifications, Channel } from '@capacitor/push-notifications';
import { Capacitor } from '@capacitor/core';

//... dentro de su servicio de inicialización...
if (Capacitor.getPlatform() === 'android') {
 const channel: Channel = {
   id: 'pedidos_criticos',
   name: 'Nuevos Pedidos',
   description: 'Notificaciones de alta prioridad para nuevos pedidos.',
   importance: 5, // Nivel 5 es "URGENTE"
   sound: 'default', // O 'custom_alert.wav' (ver Sección IX)
   vibration: true,
   visibility: 1, // VISIBILITY_PUBLIC
   lights: true,
   lightColor: '#FF0000', // Rojo
 };
 await PushNotifications.createChannel(channel);
}

Luego, cuando envíe el mensaje desde su Cloud Function (Sección VI), deberá especificar este id de canal en el payload de Android para que el sistema operativo utilice esta configuración de alta prioridad.

Sección IV: Configuración Completa de la Plataforma iOS (APNs)

Esta es la sección más compleja y propensa a errores de la configuración. La comunicación con iOS requiere una configuración criptográfica entre su cuenta de Apple Developer, Firebase y su proyecto nativo de Xcode.

Configuración del Portal de Desarrolladores de Apple

  1. Inicie sesión en su(https://developer.apple.com/).
  2. Vaya a "Certificates, Identifiers & Profiles" -> "Identifiers".
  3. Haga clic en el botón "+" para registrar un nuevo "App ID".16
  4. Seleccione "App" y continúe.
  5. Description: Un nombre para su aplicación (p. ej., "Delivery App").
  6. Bundle ID: Seleccione "Explicit" e ingrese exactamente el appId de su archivo capacitor.config.ts.16
  7. Capabilities: Desplácese hacia abajo y marque la casilla "Push Notifications".16
  8. Haga clic en "Continue" y "Register".

Estándar Moderno (2025): Generación de la Clave de Autenticación APNs .p8

El método obsoleto de certificados .p12 requería una generación manual y una renovación anual. El estándar moderno, recomendado por Apple y Firebase, utiliza una Clave de Autenticación .p8 basada en tokens, que no caduca.23

  1. En el Portal de Desarrolladores de Apple, vaya a "Keys".
  2. Haga clic en el botón "+" para crear una nueva clave.23
  3. Key Name: Ingrese un nombre descriptivo (p. ej., "Firebase Delivery Key").
  4. Marque la casilla: "Apple Push Notifications service (APNs)".26
  5. Haga clic en "Continue" y "Register".

Pasos Críticos de Descarga:

  1. Descargue el archivo .p8: Apple le permitirá descargar el archivo de clave (.p8) solo una vez. Guárdelo en un lugar seguro; si lo pierde, deberá revocar esta clave y generar una nueva.26
  2. Anote los IDs: Anote el Key ID (un valor de 10 caracteres) y su Team ID (visible en la esquina superior derecha de su cuenta).26

Información Actual (Febrero 2025): Apple ha introducido nuevas funciones de seguridad para las claves APNs.28 Ahora puede crear "Team-scoped keys" (para desarrollo o producción) y "Topic-specific keys" (asociadas con un Bundle ID específico). Para una seguridad óptima, se recomienda utilizar la nueva opción para asociar esta clave .p8 específicamente con el Bundle ID de su aplicación de delivery. Esto limita el alcance de la clave y es la mejor práctica de seguridad a partir de 2025.28

Configuración de Firebase para iOS

Ahora, conecte Firebase a APNs usando la clave .p8 que acaba de crear.

  1. En su proyecto de Firebase, vaya a "Configuración del proyecto" (icono de engranaje) -> "Cloud Messaging".27
  2. En la sección "Configuración de app para iOS", busque "Clave de autenticación de APNs".
  3. Haga clic en el botón "Subir".27
  4. Subir archivo de clave: Proporcione el archivo .p8 que descargó de Apple.
  5. ID de clave: Ingrese el Key ID de 10 caracteres que anotó.27
  6. ID de equipo: Ingrese su Team ID que anotó.27
  7. Haga clic en "Subir".

Una vez que Firebase confirme la clave, regrese al dashboard principal, haga clic en "Agregar aplicación" y seleccione el icono de iOS.15

  1. ID de paquete de iOS: Ingrese exactamente el mismo appId / "Bundle ID".15
  2. Apodo de la app: (Opcional).
  3. Haga clic en "Registrar app".
  4. Descargue GoogleService-Info.plist: Descargue este archivo de configuración. Contiene las claves específicas de iOS para que su aplicación se conecte a Firebase.15

Configuración del Proyecto Nativo (Xcode)

El último paso es configurar el proyecto nativo de iOS.

  1. Abra su proyecto en Xcode ejecutando:
    Bash
    npx cap open ios
  2. Agregar el archivo .plist: Arrastre el archivo GoogleService-Info.plist que acaba de descargar desde el Finder directamente a la raíz de la carpeta "App" (junto a AppDelegate.swift) en el navegador de proyectos de Xcode.17 Cuando se le solicite, asegúrese de que la casilla "Copy items if needed" esté marcada y que su aplicación esté seleccionada en la sección "Add to targets".
  3. Habilitar Capacidades en Xcode: Este paso es fundamental y a menudo se olvida.
    a. En el navegador de proyectos, haga clic en el nombre de su proyecto (el icono azul superior).
    b. Seleccione el target de su aplicación (generalmente "App").
    c. Vaya a la pestaña "Signing & Capabilities".
    d. Haga clic en el botón "+ Capability" en la esquina superior izquierda.16
    e. Busque y haga doble clic en "Push Notifications".15
    f. Vuelva a hacer clic en "+ Capability" y agregue "Background Modes".
    g. En la nueva sección "Background Modes", marque la casilla "Remote notifications".

Importante: Debe probar las notificaciones de iOS en un dispositivo físico (iPhone, iPad). Las notificaciones push no funcionan en el simulador de iOS.22

Sección V: Implementación del Lado del Cliente (Servicio Angular en Ionic)

Esta sección detalla el código TypeScript necesario dentro de su aplicación Ionic/Angular. La arquitectura recomendada es crear un PushNotificationService (@Injectable({ providedIn: 'root' })) que se inicialice una vez en app.component.ts.

La lógica de inicialización en app.component.ts garantiza que los listeners de notificaciones se registren tan pronto como la aplicación se inicie, lo que es esencial para manejar las notificaciones que abren la aplicación desde un estado cerrado.12

Inicialización y Solicitud de Permisos

El primer paso es solicitar permiso explícito al usuario para recibir notificaciones. En iOS, esto es obligatorio.11 En Android 13 (API 33) y versiones posteriores, también es obligatorio.

TypeScript

// En push-notification.service.ts
import { Injectable } from '@angular/core';
import { Router } from '@angular/router';
import { Capacitor } from '@capacitor/core';
import {
 PushNotifications,
 Token,
 PushNotificationSchema,
 ActionPerformed,
 PermissionStatus
} from '@capacitor/push-notifications';
// Importar controladores de UI (p. ej., ToastController) si es necesario

@Injectable({
 providedIn: 'root'
})
export class PushNotificationService {

 constructor(private router: Router) {}

 public async initPush() {
   if (Capacitor.getPlatform() === 'web') {
     return; // Los PWA se manejan de manera diferente
   }
   
   // 1. Solicitar Permisos
   await this.requestPermissions();
   
   // 2. Inicializar listeners
   this.addListeners();
 }

 private async requestPermissions() {
   let permStatus: PermissionStatus = await PushNotifications.checkPermissions();

   if (permStatus.receive === 'prompt') {
     permStatus = await PushNotifications.requestPermissions();
   }

   if (permStatus.receive!== 'granted') {
     console.warn('Permiso de notificaciones no concedido.');
     // Opcionalmente, mostrar una alerta pidiendo al usuario que habilite los permisos en la configuración.
     return;
   }

   // 3. Registrarse en FCM/APNs
   // Solo registrar si el permiso fue concedido
   await PushNotifications.register();
 }
 
 //... resto del servicio
}

Registro y Captura del Token FCM

Una vez que se llama a register(), el plugin se comunica con FCM/APNs en segundo plano. Cuando tiene éxito, se dispara el listener 'registration'. Este es el momento más importante: debe capturar este token y enviarlo a su backend (Firestore) para asociarlo con el usuario actual.14

TypeScript

// En push-notification.service.ts (continuación)

 private addListeners() {
   // Se dispara al registrarse exitosamente
   PushNotifications.addListener('registration', (token: Token) => {
     console.log('Token de registro obtenido:', token.value);
     
     //!! LÓGICA CRÍTICA DE BACKEND!!
     // Envíe este token.value a su backend (Firestore) y asócielo
     // con el ID de usuario o restaurante actualmente autenticado.
     // Ejemplo: this.firestoreService.saveTokenForUser(token.value);
   });

   // Se dispara si el registro falla
   PushNotifications.addListener('registrationError', (err: any) => {
     console.error('Error en el registro de notificaciones:', err);
   });
   
   //... más listeners a continuación
 }

Manejo de Notificaciones en Primer Plano (pushNotificationReceived)

Este listener se dispara solo si se recibe una notificación mientras la aplicación está abierta y en primer plano.11 Por defecto, el SO no muestra la notificación en este estado. Esto le da la oportunidad de mostrar una alerta en la aplicación (como un toast o un modal).12

TypeScript

// En push-notification.service.ts (continuación de addListeners)

   // Se dispara al recibir una notificación en primer plano
   PushNotifications.addListener('pushNotificationReceived',
     (notification: PushNotificationSchema) => {
       console.log('Push recibido en primer plano:', notification);
       
       // Ejemplo: Mostrar un Toast de Ionic
       // const toast = await this.toastController.create({
       //   message: notification.title,
       //   duration: 3000
       // });
       // toast.present();
     }
   );

Manejo de la Interacción del Usuario (pushNotificationActionPerformed)

Este es el listener más importante para la navegación y el deep-linking. Se dispara cuando un usuario toca la notificación en la bandeja del sistema, lo que abre la aplicación (ya sea desde el segundo plano o desde un estado cerrado).12

Aquí es donde se extrae el payload de data (ver Sección VII) para navegar al usuario a la pantalla relevante.

TypeScript

// En push-notification.service.ts (continuación de addListeners)

   // Se dispara cuando el usuario TOCA la notificación
   PushNotifications.addListener('pushNotificationActionPerformed',
     (action: ActionPerformed) => {
       console.log('Acción de push realizada:', action);
       
       // Extraer datos personalizados
       const data = action.notification.data;

       if (data.orderId) {
         // Navegar a la página específica del pedido
         this.router.navigate(['/orders', data.orderId]);
       } else {
         // Acción genérica, p. ej., ir al dashboard
         this.router.navigate(['/home']);
       }
     }
   );
 } // Fin de addListeners
} // Fin del servicio

Finalmente, asegúrese de inicializar este servicio en app.component.ts:

})
export class AppComponent implements OnInit {

 ngOnInit() {
   this.initializeApp();
 }

 initializeApp() {
   //... otra lógica de inicialización...
   
   // Inicializar el servicio de notificaciones push
   this.pushService.initPush();
 }
}

Sección VI: Arquitectura del Backend (Cloud Functions y Firestore)

El "cerebro" del sistema reside en Cloud Functions.38 Estas funciones de backend (escritas en TypeScript o Node.js) reaccionarán a los cambios en la base de datos y enviarán las notificaciones.39

Diseño de la Base de Datos: Almacenamiento de Tokens

Como se estableció en la Sección I, el modelo de datos es crucial. Los tokens se almacenarán en subcolecciones para admitir múltiples dispositivos.8

  • Para clientes: users/{userId}/fcmTokens/{tokenId}
  • Para restaurantes: restaurants/{restaurantId}/fcmTokens/{tokenId}

El documento {tokenId} debe contener el token y un createdAt timestamp para una futura limpieza de tokens obsoletos.8

Lógica Central: Creación de Triggers de Cloud Function (TypeScript)

Se necesitan dos funciones principales para el caso de uso del delivery.

Caso de Uso 1: Nuevo Pedido al Restaurante (Trigger onCreate)

Esta función se dispara cuando se crea un nuevo documento en la colección orders. Su trabajo es notificar al restaurante.41

TypeScript

// En index.ts (proyecto de Cloud Functions)
import * as functions from 'firebase-functions';
import * as admin from 'firebase-admin';

admin.initializeApp();
const db = admin.firestore();
const messaging = admin.messaging();

export const onNewOrderCreated = functions.firestore
.document('orders/{orderId}')
.onCreate(async (snapshot, context) => {
   
   const orderData = snapshot.data();
   if (!orderData) return;

   const restaurantId = orderData.restaurantId;
   const orderId = context.params.orderId;

   // 1. Obtener todos los tokens para ese restaurante

Sección VII: El Núcleo del Problema: Garantizar la Entrega en Segundo Plano y con la App Cerrada

Este es el requisito más crítico del usuario ("a pesar de que este fuera de la app") y la causa del 99% de los fracasos en las implementaciones de notificaciones push. El problema radica en la diferencia fundamental entre los payloads notification y data de FCM.

La Distinción Crítica: notification vs. data

FCM permite enviar dos tipos de mensajes 43:

  1. Mensajes de Notificación (Payload notification):
  • Qué es: Un objeto JSON con claves predefinidas: title, body, sound, icon.
  • Comportamiento (Segundo Plano / Cerrada): Estos mensajes son manejados directamente por el Sistema Operativo.37 El SO muestra la notificación en la bandeja del sistema automáticamente.
  • El Problema: El código de su aplicación (el listener pushNotificationReceived) no se ejecuta.
  1. Mensajes de Datos (Payload data):
  • Qué es: Un objeto JSON con claves y valores personalizados (p. ej., {"orderId": "12345"}).
  • Comportamiento (Segundo Plano / Cerrada): El SO recibe el mensaje pero no hace nada con él. No se muestra ninguna notificación visual.44 El mensaje se "despierta" silenciosamente en su aplicación, pero el plugin de Capacitor no lo procesará a menos que se implemente código nativo personalizado (lo cual queremos evitar).11
  • Comportamiento (Primer Plano): El mensaje se entrega directamente al listener pushNotificationReceived.43

La Solución: El Payload Mixto (notification + data)

El problema es claro:

  • Si envía solo notification, obtiene una alerta visual pero no puede pasar datos de deep-linking de manera fiable a su listener pushNotificationActionPerformed.
  • Si envía solo data, su aplicación recibe los datos (en primer plano) pero no se muestra ninguna notificación cuando la aplicación está cerrada. Un fracaso total para un delivery.

La única arquitectura de payload fiable para este caso de uso es enviar ambos payloads en el mismo mensaje.37

  • El objeto notification le dice al SO: "Muestra esta notificación visual en la bandeja del sistema".
  • El objeto data "viaja" junto con esa notificación.
  • Cuando el usuario toca la notificación (que fue mostrada por el SO), el SO abre la aplicación. El plugin de Capacitor es lo suficientemente inteligente como para interceptar esta apertura, extraer el payload data que venía adjunto y entregárselo limpiamente a su listener pushNotificationActionPerformed (Sección V).

Esto le da lo mejor de ambos mundos: visibilidad garantizada por el SO y capacidad de deep-linking a través de su código Angular.

Mejora Específica de Android: click_action

Existe una peculiaridad de Android en la que, a veces, cuando la aplicación está completamente cerrada (estado killed), tocar la notificación solo abre la aplicación pero no dispara el listener pushNotificationActionPerformed.

La solución es doble 37:

  1. En la Cloud Function: Al construir el payload, agregue la propiedad click_action: 'FCM_PLUGIN_ACTIVITY' dentro del objeto notification.
    JavaScript
    // Payload de ejemplo en la Cloud Function
    const payload = {
         notification: {
           title: '¡Nuevo Pedido!',
           body: '...',
           click_action: 'FCM_PLUGIN_ACTIVITY' // <-- ¡IMPORTANTE!
     },
         data: {
           orderId: '12345'
     },
         //...
    };
  2. En el Proyecto Android: Edite manualmente el archivo android/app/src/main/AndroidManifest.xml y agregue el siguiente intent-filter dentro de la etiqueta <activity> principal (.MainActivity):
    XML
    <activity...>
         <intent-filter>
             <action android:name="FCM_PLUGIN_ACTIVITY" />
             <category android:name="android.intent.category.DEFAULT" />
         </intent-filter>

    </activity>

Esto crea un vínculo explícito entre la notificación y la Actividad principal de su aplicación, asegurando que el plugin de Capacitor reciba el evento de "clic" de manera fiable.

Sección VIII: Guía de Solución de Problemas (Troubleshooting) y Pasos Finales

Cuando las notificaciones fallan, el proceso de depuración puede ser frustrante. Siga este plan para aislar el problema.

Paso 1: Aislar el Problema (Cliente vs. Backend)

El método más eficaz es usar la herramienta de "Enviar mensaje de prueba" en la Consola de Firebase.46

  1. Ejecute su aplicación en un dispositivo físico.
  2. Mire los registros de la consola (Xcode o Android Studio Logcat) para el listener registration (Sección V).
  3. Copie el Token FCM que se imprime en la consola.
  4. Vaya a su Consola de Firebase -> "Cloud Messaging" -> "Crear campaña" -> "Mensaje de prueba".
  5. Pegue el Token FCM que copió.
  6. Envíe un mensaje de prueba simple (solo título y cuerpo).
  7. Observe el resultado:
  • Si la notificación LLEGA: ¡Felicidades! Toda su configuración del lado del cliente (APNs, .p8, google-services.json, código de Capacitor) es CORRECTA. El problema está 100% en su Cloud Function (Sección VI).
  • Si la notificación NO LLEGA: El problema está en su configuración del lado del cliente (Secciones III, IV, V). Su Cloud Function ni siquiera importa en este punto.

Lista de Verificación de Problemas del Lado del Cliente (Si la Prueba de Consola Falla)

Específico de iOS:

  • ¿Está probando en un dispositivo físico? (Las notificaciones push NO funcionan en el simulador de iOS).22
  • ¿Habilitó la capacidad "Push Notifications" en Xcode?.16
  • ¿Habilitó la capacidad "Remote notifications" en "Background Modes" en Xcode?
  • ¿Subió el archivo .p8 (no un .p12), el Key ID y el Team ID correctos a Firebase?.26
  • ¿Arrastró el GoogleService-Info.plist al proyecto de Xcode y lo agregó al target?.17
  • ¿Coincide exactamente el Bundle ID de Xcode con el appId de Capacitor y el ID de paquete en Firebase?.16

Específico de Android:

  • ¿Está el archivo google-services.json en la carpeta android/app/?.18
  • ¿Coincide exactamente el nombre del paquete en build.gradle con el appId de Capacitor y el nombre del paquete en Firebase?.12
  • ¿Creó un Canal de Notificación (Sección III)? En dispositivos Android 8+, las notificaciones sin canal fallan silenciosamente.19

Ambas Plataformas:

  • ¿Llamó a PushNotifications.requestPermissions() y el usuario otorgó permiso?.11
  • ¿Llamó a PushNotifications.register()?
  • ¿Se está disparando el listener registration y devolviendo un token? Si se dispara registrationError, lea el error.19

Lista de Verificación de Problemas del Lado del Backend (Si la Prueba de Consola Funciona)

  • Revise los Logs de la Cloud Function: Vaya a la Consola de Firebase -> "Functions" -> "Registros". ¿Se está disparando su trigger (onCreate o onUpdate)? ¿Hay algún error (permission-denied, undefined, etc.)?
  • Errores de Consulta: ¿Su consulta de Firestore para los tokens (p. ej., db.collection(\users/${userId}/fcmTokens`).get()) está devolviendo documentos? Verifique que userIdno seaundefined` y que los tokens existan en esa ruta.
  • Payload Incorrecto: ¿Está enviando solo un payload data? Recuerde, esto no se mostrará visualmente en el fondo.44 Debe enviar el payload mixto (notification + data) como se describe en la Sección VII.
  • Tokens Obsoletos: Es posible que esté enviando a tokens que han caducado o han sido desinstalados. El objeto de respuesta de messaging.sendToDevice() le indicará qué tokens fallaron. Debe implementar una lógica para eliminar estos tokens "no registrados" de su base de datos.8

Sección IX: Conclusión y Recomendaciones de Nivel de Producción

Para construir un sistema de notificaciones de nivel de delivery que sea fiable, la implementación debe tratarse como una característica central de la arquitectura, no como un complemento. El éxito depende de cuatro pilares fundamentales:

  1. Arquitectura Impulsada por Eventos: La lógica de negocio debe residir en Cloud Functions que se activan por cambios de estado en Firestore (onUpdate, onCreate).
  2. Modelo de Datos de Token Uno-a-Muchos: El uso de subcolecciones (.../fcmTokens/) es la única forma de admitir de manera fiable múltiples dispositivos por usuario o restaurante.
  3. Configuración Nativa Meticulosa: La configuración de Android (Canales de Notificación) y iOS (claves .p8 y capacidades de Xcode) debe ser perfecta.
  4. Payload Mixto (notification + data): Esta es la clave para lograr tanto la visibilidad de la notificación en segundo plano como la capacidad de deep-linking controlada por la aplicación.

Recomendaciones Finales para Producción

  • Gestión de Tokens Obsoletos: Las aplicaciones se desinstalan. Los tokens caducan.8 Cuando admin.messaging().sendToDevice() devuelva un error indicando que un token no es válido (p. ej., messaging/registration-token-not-registered), su Cloud Function debe eliminar ese token de Firestore para evitar envíos fallidos y mejorar la eficiencia.
  • Sonidos de Notificación Personalizados: Para que un restaurante note un nuevo pedido, un sonido genérico no es suficiente.
  • Android: Agregue su archivo de sonido (p. ej., order_alert.wav) a android/app/src/main/res/raw/. Especifique este nombre de archivo (sin la extensión) en la propiedad sound de su Canal de Notificación (Sección III).
  • iOS: Agregue su archivo de sonido (p. ej., order_alert.caf) a la carpeta App/Resources en Xcode. Especifique el nombre del archivo en el payload de APNs enviado desde su Cloud Function (p. ej., apns: { payload: { aps: { sound: 'order_alert.caf' } } }).
  • Pruebas Rigurosas de Estado: Pruebe exhaustivamente todos los estados de la aplicación:
  1. Primer Plano: La app está abierta. (Debería ver un toast en la app).
  2. Segundo Plano: La app está minimizada. (Debería ver una notificación del sistema).
  3. Cerrada (Killed): La app ha sido deslizada y eliminada de la memoria. (Debería ver una notificación del sistema y el deep-linking debe funcionar al tocarla).
